# 1. 프로젝트 개요

## 1.1 프로젝트명

**OURSPOT — 우리 여기 가자**

부제: *가고 싶었던 곳부터 함께한 순간까지.*

## 1.2 기획 배경

연인과 일상적인 대화를 나누거나 SNS 콘텐츠를 공유하다 보면 함께 방문하고 싶은 장소가 자주 생긴다.

하지만 이러한 장소 정보는 메신저 대화, 인스타그램 게시물, 지도 애플리케이션 등에 분산되어 관리된다. 이로 인해 실제 데이트를 계획할 때 과거에 가기로 했던 장소를 기억하지 못하거나, 같은 장소를 다시 검색하게 되는 불편함이 발생한다.

또한 실제로 장소를 방문한 이후에는 방문 전 기대했던 점과 방문 후 경험을 비교하거나 기록할 수 있는 공간이 부족하다.

OURSPOT은 이러한 문제에서 출발한 커플 전용 웹 서비스이다.

연인 두 사람이 가고 싶은 장소를 함께 저장하고, 저장한 장소를 활용해 날짜별 데이트를 계획하며, 방문 전후의 생각과 경험을 기록할 수 있도록 한다.

## 1.3 프로젝트 목적

### 서비스 측면

1. 연인과 가고 싶은 장소를 한곳에 저장한다.
2. 두 사람이 서로 다른 계정으로 로그인해 동일한 장소 목록을 공유한다.
3. 저장한 장소를 날짜별로 배치하여 데이트 일정을 미리 계획한다.
4. 방문 전 기대와 방문 후 감상을 각각 기록한다.
5. 오래전에 저장했지만 아직 방문하지 않은 장소를 다시 확인할 수 있도록 한다.

### 기술적 측면

1. 6개 이상의 Docker 컨테이너로 웹 서비스 실행 환경을 구축한다.
2. Nginx Reverse Proxy를 통해 외부 요청을 처리한다.
3. 서로 다른 역할을 담당하는 2개의 백엔드 서버를 구성한다.
4. Redis 기반 세션 공유를 통해 서버 간 사용자 인증 상태를 유지한다.
5. MySQL에 사용자 및 서비스 데이터를 저장한다.
6. Docker Volume Mount를 통해 데이터 영속성을 확보한다.
7. 개발한 Docker 이미지를 개인 Docker Hub에 배포한다.
8. 컨테이너 실행 명령어와 설치 절차를 문서화해 동일한 환경에서 서비스를 재현할 수 있도록 한다.

## 1.4 개발 방향

본 프로젝트는 상용 서비스 출시가 아니라 클라우드네이티브 과목의 기말고사 대체과제를 목적으로 한다.

따라서 다음 원칙을 적용한다.

- 서비스 기능은 실사용 가능성을 유지하는 최소 범위로 제한한다.
- 개발 복잡도가 높은 외부 서비스 연동은 제외한다.
- 애플리케이션 기능보다 컨테이너 간 통신과 세션 공유의 정확성을 우선한다.
- 기능 구현과 동시에 평가에 필요한 검증자료를 확보한다.
- 구현하지 않은 기능이나 검증하지 않은 항목을 완료된 것으로 보고하지 않는다.

# 2. 서비스 대상 및 사용 환경

## 2.1 대상 사용자

연인 관계의 두 사용자로 한정한다.

초기 버전에서는 한 쌍의 커플만 사용하는 소규모 서비스로 구현한다.

사용자들은 각자 고유한 로그인 계정을 가지지만 동일한 장소 데이터에 접근한다.

## 2.2 사용자 계정 구성

회원가입 기능은 구현하지 않는다.

서비스 설치 시 MySQL 데이터베이스에 다음 두 개의 테스트 계정을 사전 등록한다.

| 항목 | 사용자 A | 사용자 B |
| --- | --- | --- |
| 사용자 ID | `user_a` | `user_b` |
| 표시 이름 | 사용자 A | 사용자 B |
| 로그인 계정 | 별도 계정 | 별도 계정 |
| 커플 식별자 | `couple_001` | `couple_001` |

두 계정은 동일한 `couple_id`를 사용한다.

비밀번호는 평문으로 저장하지 않고 해시값으로 저장한다.

**사전 등록되는 것은 사용자 계정뿐이며, 로그인 기능과 사용자 인증 과정은 실제로 구현한다.**

사용자는 로그인하지 않으면 장소 데이터에 접근할 수 없다.

## 2.3 서비스 사용 범위

- 사용자 A와 B는 각자 로그인한다.
- 두 사람이 등록한 장소는 공동 목록에 표시된다.
- 장소를 등록한 사람이 누구인지 확인할 수 있다.
- 데이트 계획은 공동으로 조회하고 수정할 수 있다.
- 방문 전후 코멘트는 각자의 계정으로 작성한다.
- 다른 사람의 코멘트는 조회할 수 있지만 수정하거나 삭제할 수 없다.

# 3. 서비스 핵심 기능

## 3.1 기능 요구사항

| ID | 기능명 | 상세 기능 | 우선순위 |
| --- | --- | --- | --- |
| F-01 | 로그인 | 사전 등록된 계정으로 로그인 | 필수 |
| F-02 | 로그아웃 | 현재 로그인 세션 종료 | 필수 |
| F-03 | 사용자 확인 | 로그인한 사용자 정보 확인 | 필수 |
| F-04 | 장소 등록 | 장소명, 링크, 카테고리, 메모 저장 | 필수 |
| F-05 | 장소 조회 | 두 사람이 등록한 장소 공동 조회 | 필수 |
| F-06 | 장소 수정·삭제 | 저장된 장소 정보 변경 및 삭제 | 필수 |
| F-07 | 방문 상태 관리 | 미방문·방문 완료 구분 | 필수 |

| F-12 | 잊힌 장소 표시 | 오래된 미방문 장소 우선 조회 | 차별화 |

여기서 필수는 **본 프로젝트에서 구현하기로 결정한 필수 기능**을 의미하며, 교수님이 모든 세부 기능을 개별적으로 요구했다는 뜻은 아니다.

## 3.2 장소 저장

사용자는 가고 싶은 장소를 직접 등록한다.

### 입력 정보

| 항목 | 필수 여부 | 설명 |
| --- | --- | --- |
| 장소명 | 필수 | 가고 싶은 장소 이름 |
| 카테고리 | 필수 | 카페, 맛집, 놀거리, 기타 |
| URL | 선택 | 인스타그램·지도·웹페이지 링크 |
| 메모 | 선택 | 장소를 저장한 이유 또는 간단한 설명 |

등록자와 등록일은 로그인 정보와 시스템 시간을 이용해 자동으로 기록한다.

장소 등록 시 방문 상태는 기본적으로 '미방문'으로 설정한다.

인스타그램 URL에서 장소 정보를 자동 추출하지 않고, 사용자가 직접 입력하도록 한다.

## 3.3 공유 장소 보관함

로그인 후 메인 화면에 두 사람이 함께 저장한 장소 목록을 표시한다.

장소 보관함에서는 다음 정보를 확인한다.

- 장소명 및 카테고리
- 장소 관련 링크
- 등록한 사용자
- 저장 날짜
- 방문 상태
- 데이트 예정일
- 방문 전후 코멘트

미방문 장소와 방문 완료 장소를 탭으로 구분한다.

## 3.4 날짜별 데이트 계획

사용자는 저장해둔 장소를 선택해 특정 날짜의 데이트 계획에 배정할 수 있다.

### 사용 예시

**2026년 11월 14일 — 을지로 데이트**

| 방문 순서 | 장소 | 유형 |
| --- | --- | --- |
| 1 | 파스타집 | 맛집 |
| 2 | 빈티지 카페 | 카페 |
| 3 | 소품샵 | 놀거리 |

사용자는 장소를 추가할 때 예정일과 방문 순서를 지정한다.

날짜를 선택하면 해당 날짜에 배정된 장소들이 방문 순서대로 표시된다.

### 구현 범위

- 날짜 선택
- 기존 저장 장소를 일정에 추가
- 동일 날짜에 여러 장소 배정
- 방문 순서 지정 및 수정
- 일정에서 장소 제외
- 날짜별 데이트 계획 조회

### 구현 제한

개발 복잡도를 줄이기 위해 한 장소는 동시에 하나의 예정일에만 배정하도록 한다.

데이트 계획 자체의 제목, 예산, 출발 시간, 이동 경로, 교통편, 예약 기능은 구현하지 않는다.

날짜별 계획은 별도의 외부 캘린더를 사용하지 않고 HTML 날짜 입력과 MySQL의 DATE 데이터를 활용한다.

## 3.5 방문 상태 관리

장소는 다음 두 가지 상태를 가진다.

| 상태 | 설명 |
| --- | --- |
| 미방문 | 저장했지만 아직 방문하지 않은 장소 |
| 방문 완료 | 실제 방문을 마친 장소 |

사용자가 방문 완료 버튼을 누르면 방문 상태와 방문 완료 일시가 저장된다.

방문 후 코멘트가 존재하는 장소는 코멘트를 삭제하거나 정리한 후에만 미방문 상태로 되돌리도록 한다. 이를 통해 기록의 의미가 서로 충돌하지 않도록 한다.

## 3.6 방문 전후 코멘트

두 사용자는 한 장소에 대해 각각 다음 두 가지 코멘트를 작성할 수 있다.

**방문 전 코멘트**

- 장소에 기대하는 점
- 가보고 싶은 이유
- 방문 전에 떠오른 생각

**방문 후 코멘트**

- 실제 방문 경험
- 기대와 달랐던 점
- 기억에 남는 점

### 작성 규칙

- 사용자별·장소별·시점별 코멘트는 각각 최대 1개로 제한한다.
- 작성한 코멘트는 본인만 수정하거나 삭제할 수 있다.
- 두 사람 모두 상대방의 코멘트를 조회할 수 있다.
- 방문 전 코멘트는 미방문 상태에서 작성한다.
- 방문 후 코멘트는 방문 완료 상태에서 작성한다.

별점, 대댓글, 좋아요 및 이미지 업로드 기능은 구현하지 않는다.

## 3.7 잊힌 장소 다시 보기

본 서비스의 차별화 기능이다.

미방문 장소를 저장일 기준 오래된 순서로 정렬하고, 일정 기간 이상 방문하지 않은 장소를 구분해 표시한다.

예를 들어 저장 후 30일 이상 지난 장소에 '아직 못 간 곳'이라는 표시를 제공한다.

별도의 AI 추천 기능 없이 데이터베이스의 저장일과 현재 날짜 차이만으로 구현한다.

# 4. 화면 구성

프론트엔드는 HTML, CSS, Vanilla JavaScript로 구현한다.

React와 Vue는 사용하지 않는다.

## 4.1 로그인 화면

**주요 구성**

- 서비스 로고 및 이름
- 이메일 입력란
- 비밀번호 입력란
- 로그인 버튼
- 로그인 실패 안내

**동작**

로그인 버튼 클릭 시 User API로 요청한다.

인증 성공 시 세션 쿠키를 발급받고 메인 화면으로 이동한다.

## 4.2 메인 화면 — 장소 보관함

**주요 구성**

- 사용자 이름
- 로그아웃 버튼
- 미방문 장소 개수
- 방문 완료 장소 개수
- 장소 목록
- 장소 등록 버튼
- 미방문·방문 완료 필터
- 날짜별 계획 화면 이동 버튼

장소를 선택하면 상세정보와 코멘트를 확인할 수 있다.

## 4.3 장소 등록·수정 화면

별도 페이지를 만들지 않고 모달 또는 화면 내 폼으로 구현한다.

입력 항목은 장소명, 카테고리, URL, 메모로 제한한다.

입력값 검증 후 Place API에 데이터를 전송한다.

## 4.4 날짜별 데이트 계획 화면

**주요 구성**

- 날짜 선택
- 선택한 날짜에 배정된 장소 목록
- 방문 순서
- 저장한 장소 추가 버튼
- 방문 순서 수정
- 일정에서 장소 제외

월간 캘린더 전체를 직접 구현할 필요는 없다.

HTML의 날짜 선택 기능을 활용하고 선택된 날짜에 해당하는 계획을 조회하는 방식으로 구현한다.

## 4.5 장소 상세 및 코멘트 화면

**주요 구성**

- 장소 기본 정보
- 방문 예정일
- 방문 상태
- 사용자 A·B의 방문 전 코멘트
- 사용자 A·B의 방문 후 코멘트
- 본인 코멘트 작성·수정 버튼

코멘트 작성 시점에 따라 입력란을 구분한다.

# 5. 시스템 아키텍처

## 5.1 전체 구성

서비스는 Docker 기반 6개 컨테이너로 구성한다.

외부 요청은 Nginx 역방향 프록시 컨테이너를 통해 전달한다.

프론트엔드, 사용자 인증 API, 장소 관리 API는 각각 독립된 컨테이너로 실행한다.

두 백엔드는 Redis에 저장된 사용자 세션을 공유하며, MySQL에 저장된 데이터를 사용한다.

## 5.2 컨테이너 구성표

| 번호 | 컨테이너명 | 기술 | 역할 | 내부 포트 |
| --- | --- | --- | --- | --- |
| 1 | `ourspot-proxy` | Nginx | Reverse Proxy 및 요청 분기 | 80 |
| 2 | `ourspot-front` | Apache HTTP Server | 정적 HTML/CSS/JS 제공 | 80 |
| 3 | `ourspot-user-api` | Node.js Express | 로그인·로그아웃·사용자 인증 | 3000 |
| 4 | `ourspot-place-api` | Node.js Express | 장소·데이트 계획·코멘트 관리 | 3000 |
| 5 | `ourspot-db` | MySQL | 영구 데이터 저장 | 3306 |
| 6 | `ourspot-redis` | Redis | 사용자 세션 공유 | 6379 |

## 5.3 Docker 네트워크

**네트워크명:** `ourspot-net`

6개 컨테이너를 동일한 사용자 정의 Docker Bridge Network에 연결한다.

컨테이너 간에는 Docker DNS 기능을 활용해 컨테이너 이름으로 접근한다.

개발 및 검증 시 Ubuntu Host의 `8080` 포트를 Nginx 컨테이너의 `80` 포트와 연결한다.

외부 접근 경로는 다음과 같다.

`http://<Ubuntu-Host-IP>:8080`

MySQL, Redis, 두 백엔드 API 서버는 외부에 직접 포트를 공개하지 않는다.

다만 필요 시 개발 중에만 별도의 진단용 포트를 사용할 수 있으며, 최종 실행 구성에서는 제거한다.

## 5.4 Nginx 요청 라우팅

| URL 경로 | 전달 대상 |
| --- | --- |
| `/` | `ourspot-front:80` |
| `/api/auth/*` | `ourspot-user-api:3000` |
| `/api/places/*` | `ourspot-place-api:3000` |

데이트 일정 및 코멘트 기능은 Place API의 하위 경로에서 처리한다.

프록시 설정 시 원래 요청 경로와 필요한 HTTP 헤더, 쿠키가 백엔드까지 전달되도록 한다.

## 5.5 마이크로서비스 역할 분리

### User API

담당 기능:

- 사용자 로그인
- 사용자 로그아웃
- 로그인 사용자 정보 조회
- MySQL 사용자 인증
- Redis 세션 생성 및 종료

### Place API

담당 기능:

- 로그인 세션 확인
- 공유 장소 CRUD
- 방문 상태 관리
- 날짜별 데이트 계획
- 방문 전후 코멘트 관리
- 미방문 장소 정렬

두 백엔드는 각자 독립적으로 실행되고, 서로 다른 API 요청을 처리한다.

기술 스택은 동일한 Node.js Express를 사용하되, 비즈니스 기능을 구분하여 분리한다.

이기종 서버 구성에 따른 가점은 추후 개발 여유에 따라 검토한다.

# 6. Redis 기반 사용자 인증 및 세션 공유

## 6.1 설계 목적

HTTP 요청은 기본적으로 독립적으로 처리된다.

따라서 사용자가 User API에서 로그인한 후 Place API에 요청하더라도 로그인 상태를 유지할 수 있는 공통 세션 저장소가 필요하다.

이를 위해 Redis를 세션 저장소로 사용한다.

## 6.2 로그인 처리 절차

1. 사용자가 로그인 화면에서 계정 정보를 입력한다.
2. 브라우저가 Nginx를 통해 User API에 로그인 요청을 보낸다.
3. User API가 MySQL에서 사용자 계정을 조회한다.
4. 저장된 비밀번호 해시와 입력 비밀번호를 비교한다.
5. 인증 성공 시 세션을 생성한다.
6. 세션에 `userId`와 `coupleId`를 저장한다.
7. 세션 데이터는 Redis에 저장한다.
8. 브라우저에 세션 ID 쿠키를 발급한다.
9. 로그인 후 메인 화면에 접근한다.

## 6.3 서버 간 세션 공유 절차

1. 로그인한 사용자가 장소 목록을 요청한다.
2. 브라우저가 세션 쿠키를 포함하여 요청을 전송한다.
3. Nginx가 요청을 Place API로 전달한다.
4. Place API는 세션 ID를 이용해 Redis에서 세션 데이터를 조회한다.
5. 조회한 사용자 정보를 기반으로 인증 상태를 확인한다.
6. 해당 사용자에게 허용된 장소 데이터를 MySQL에서 조회한다.
7. 응답 결과를 브라우저에 반환한다.

## 6.4 세션 공유 구현 조건

두 백엔드에 다음 설정을 동일하게 적용한다.

- 동일한 Redis 서버 주소
- 동일한 세션 저장 키 규칙
- 동일한 세션 쿠키 이름
- 동일한 세션 서명용 비밀키
- 동일한 쿠키 경로 및 세션 유효기간
- 세션 데이터를 복원할 수 있는 호환 가능한 저장 형식

브라우저 쿠키는 HttpOnly 및 SameSite 등의 설정을 적용한다.

HTTP 기반 로컬 실습과 실제 HTTPS 배포 환경의 쿠키 보안 설정을 구분한다.

세션 ID와 비밀번호를 소스코드에 직접 기록하지 않는다.

## 6.5 세션 검증 시나리오

**테스트 1 — 로그인 및 세션 생성**

- User API를 통해 로그인한다.
- Redis에서 새 세션이 생성되었는지 확인한다.

**테스트 2 — 다른 서버에서의 세션 유지**

- 로그인 상태에서 Place API를 호출한다.
- Place API가 동일한 세션을 조회하고 정상 응답하는지 확인한다.

**테스트 3 — 비로그인 접근 제한**

- 로그아웃 후 Place API를 호출한다.
- 인증되지 않은 요청이 거부되는지 확인한다.

**테스트 4 — 사용자 계정 구분**

- 사용자 A와 B가 각각 로그인한다.
- 두 계정은 다른 세션을 갖지만 동일한 커플 공유 데이터에 접근하는지 확인한다.

# 7. 데이터베이스 설계

## 7.1 DBMS 선정

**MySQL**

선정 이유:

- 강의 실습과 연계 가능
- 사용자·장소·코멘트 데이터의 관계를 표현하기 용이
- 날짜별 조회와 정렬을 SQL로 구현할 수 있음
- Docker Volume Mount 및 데이터 영속성 검증 가능

데이터베이스명은 `ourspot`으로 한다.

## 7.2 users 테이블

| 컬럼 | 데이터 유형 | 설명 |
| --- | --- | --- |
| `id` | INT, PK | 사용자 ID |
| `email` | VARCHAR | 로그인 이메일 |
| `password_hash` | VARCHAR | 해시된 비밀번호 |
| `display_name` | VARCHAR | 사용자 표시 이름 |
| `couple_id` | VARCHAR | 커플 공유 식별자 |

초기 데이터로 두 개의 사용자 계정을 생성한다.

## 7.3 places 테이블

| 컬럼 | 데이터 유형 | 설명 |
| --- | --- | --- |
| `id` | INT, PK | 장소 ID |
| `couple_id` | VARCHAR | 공유 식별자 |
| `added_by` | INT, FK | 장소 등록자 |
| `title` | VARCHAR | 장소명 |
| `category` | VARCHAR | 장소 유형 |
| `source_url` | VARCHAR | 참고 링크 |
| `memo` | TEXT | 장소 메모 |
| `planned_date` | DATE, NULL | 데이트 예정일 |
| `visit_order` | INT, NULL | 해당 날짜의 방문 순서 |
| `is_visited` | BOOLEAN | 방문 여부 |
| `visited_at` | DATETIME, NULL | 방문 완료 시각 |
| `created_at` | DATETIME | 등록 시각 |
| `updated_at` | DATETIME | 수정 시각 |

`planned_date`가 같은 장소들을 `visit_order` 기준으로 정렬하여 날짜별 데이트 계획을 구성한다.

별도의 일정 테이블을 만들지 않아 데이터 모델과 API를 단순하게 유지한다.

## 7.4 place_comments 테이블

| 컬럼 | 데이터 유형 | 설명 |
| --- | --- | --- |
| `id` | INT, PK | 코멘트 ID |
| `place_id` | INT, FK | 장소 ID |
| `user_id` | INT, FK | 작성자 ID |
| `phase` | ENUM | `before` 또는 `after` |
| `content` | TEXT | 코멘트 내용 |
| `created_at` | DATETIME | 작성 시각 |
| `updated_at` | DATETIME | 수정 시각 |

`place_id`, `user_id`, `phase` 조합에는 UNIQUE 제약조건을 적용한다.

따라서 한 사용자가 하나의 장소에 대해 방문 전 코멘트와 방문 후 코멘트를 각각 최대 1개씩 작성하도록 한다.

## 7.5 접근 제어 및 데이터 무결성

- 모든 장소 조회에는 로그인 세션의 `coupleId`를 적용한다.
- 장소 ID만 알고 있다고 다른 커플의 데이터에 접근할 수 없도록 한다.
- 코멘트 수정·삭제 시 작성자 ID를 검증한다.
- SQL은 파라미터 바인딩 방식으로 실행한다.
- 클라이언트 입력값은 서버에서 다시 검증한다.
- 사용자가 등록한 텍스트는 화면에 출력할 때 안전하게 처리한다.
- 장소 삭제 시 관련 코멘트도 정리되도록 참조 무결성을 설정한다.

# 8. API 설계

## 8.1 사용자 인증 API

| Method | Endpoint | 기능 |
| --- | --- | --- |
| POST | `/api/auth/login` | 로그인 |
| POST | `/api/auth/logout` | 로그아웃 |
| GET | `/api/auth/me` | 현재 사용자 정보 확인 |

## 8.2 장소 관리 API

| Method | Endpoint | 기능 |
| --- | --- | --- |
| GET | `/api/places` | 장소 목록 조회 |
| POST | `/api/places` | 장소 등록 |
| GET | `/api/places/:id` | 장소 상세 조회 |
| PATCH | `/api/places/:id` | 장소 정보·예정일·방문 순서·방문 상태 수정 |
| DELETE | `/api/places/:id` | 장소 삭제 |

`GET /api/places` 요청에서는 상태 및 날짜 조건을 쿼리 파라미터로 전달할 수 있도록 한다.

예시:

- `?status=unvisited`
- `?status=visited`
- `?planned_date=2026-11-14`
- `?sort=oldest`

## 8.3 코멘트 API

| Method | Endpoint | 기능 |
| --- | --- | --- |
| GET | `/api/places/:id/comments` | 장소별 코멘트 조회 |
| PUT | `/api/places/:id/comments/:phase` | 본인의 방문 전·후 코멘트 작성·수정 |
| DELETE | `/api/places/:id/comments/:phase` | 본인의 코멘트 삭제 |

작성자 정보는 HTTP 요청 본문이 아니라 로그인 세션에서 가져온다.

## 8.4 데이터 통신

프론트엔드는 Fetch API를 사용해 백엔드와 비동기 통신한다.

백엔드 API는 JSON 데이터를 반환한다.

성공 및 오류 응답에는 적절한 HTTP 상태 코드를 사용한다.

# 9. Docker 환경 및 배포 계획

## 9.1 기술 스택

| 구분 | 기술 |
| --- | --- |
| 운영 환경 | Ubuntu Linux |
| 컨테이너 | Docker |
| Reverse Proxy | Nginx |
| Frontend | HTML5, CSS3, Vanilla JavaScript |
| Frontend 웹 서버 | Apache HTTP Server |
| Backend | Node.js Express |
| Session Store | Redis |
| Database | MySQL |
| 이미지 저장소 | Docker Hub |
| 통신 | HTTP 및 JSON API |
| 데이터 영속성 | Docker Volume Mount |

각 Docker 이미지 및 런타임의 구체적인 버전은 호환성 테스트 이후 확정하고, 보고서에 기록한다.

## 9.2 Docker 이미지 구성

### 직접 빌드할 이미지

1. `ourspot-front`
2. `ourspot-user-api`
3. `ourspot-place-api`

각 서비스의 Dockerfile을 작성한다.

개발한 소스코드는 Dockerfile의 `COPY` 명령으로 이미지 내부에 포함한다.

배포 시 개발용 소스 바인드 마운트가 없어도 실행되도록 한다.

### 기존 이미지를 활용할 컨테이너

1. Nginx Reverse Proxy
2. MySQL
3. Redis

이 컨테이너들은 공식 이미지를 기반으로 실행한다.

Nginx는 프로젝트별 라우팅 설정 파일을 별도로 제공하고, 컨테이너 실행 시 읽기 전용으로 연결한다.

공식 이미지를 새롭게 빌드할 필요는 없지만 실제 사용한 이미지명과 버전, 실행 명령어, 설치 절차를 빠짐없이 문서화한다.

## 9.3 Docker Hub 배포

직접 개발한 세 개의 이미지를 개인 Docker Hub에 업로드한다.

계획된 이미지명은 다음과 같다.

- `<DockerHubID>/ourspot-front:1.0`
- `<DockerHubID>/ourspot-user-api:1.0`
- `<DockerHubID>/ourspot-place-api:1.0`

실제 제출 시에는 `<DockerHubID>`를 자신의 계정으로 변경한다.

최종 이미지 태그와 설치 명령어가 일치해야 한다.

## 9.4 MySQL 데이터 영속성

MySQL 데이터가 저장되는 `/var/lib/mysql` 경로에 Docker Volume을 연결한다.

**Volume 이름:** `ourspot-db-data`

검증 절차는 다음과 같다.

1. MySQL 컨테이너에 Volume을 연결하고 실행한다.
2. 장소와 코멘트 데이터를 저장한다.
3. 저장된 데이터의 존재를 확인한다.
4. MySQL 컨테이너를 재시작한다.
5. 동일한 데이터를 다시 조회한다.
6. 데이터가 유지됨을 확인한다.
7. Volume 연결 상태를 Docker 명령어로 검증한다.

가능하다면 컨테이너를 삭제한 뒤 동일한 Volume을 연결하여 재생성하는 추가 검증도 수행한다.

**주의:** 데이터 영속성 검증을 수행하는 동안 해당 Volume을 삭제하지 않는다.

## 9.5 DB 초기화와 백업

최초 설치를 위한 SQL 초기화 파일을 준비한다.

초기화 파일에는 다음 내용을 포함한다.

- 데이터베이스 테이블 생성
- 사용자 A·B 테스트 계정 등록
- 테이블 관계 및 제약조건 설정
- 필요한 최소 예제 데이터

DB 백업 SQL과 복원 방법을 설치 문서에 포함한다.

초기화 SQL은 빈 DB 데이터 디렉터리에서 처음 실행할 때 적용하고, 기존 데이터가 있는 볼륨을 재사용할 때는 불필요하게 다시 초기화하지 않도록 한다.

11. 전체 컨테이너 상태 확인
12. 브라우저 접속 및 로그인 테스트

실행에 사용한 모든 `docker build`, `docker run` 명령어를 실제 실행 순서대로 기록한다.

설치 명령어에는 이미지 태그, 네트워크 이름, 환경변수, Volume, 포트 설정을 정확히 포함한다.

비밀번호와 세션 비밀키는 소스코드 또는 공개 이미지에 포함하지 않고 별도 환경설정 파일을 통해 제공한다.

제출용 설치 가이드에는 민감정보가 아닌 테스트 환경용 설정 방법만 안내한다.

## 10.3 서버 간 세션 공유 증명

로그인 기능이 정상 작동한다는 화면만으로는 서버 간 세션 공유를 충분히 증명하기 어렵다.

따라서 다음 증빙을 함께 확보한다.

1. User API 로그인 성공 화면
2. Redis에 세션이 저장된 상태를 확인한 화면
3. Place API에서 동일 세션을 이용한 인증 성공 화면
4. 다른 백엔드에서 동일한 사용자 ID가 확인되는 결과
5. 로그아웃 후 장소 API 요청이 거부되는 결과

가능하다면 User API와 Place API에서 요청을 처리한 컨테이너명을 구분해 기록하여, 요청이 실제로 다른 서버에서 처리되었음을 보여준다.

## 10.4 DB 영속성 증명

1. 장소 데이터 저장
2. 저장된 DB 레코드 확인
3. MySQL 컨테이너 재시작
4. DB 연결 복구 확인
5. 동일한 장소·코멘트 조회
6. Volume 연결 상태 확인

재시작 전후 동일한 데이터 ID와 내용이 유지됨을 캡처한다.

| DB 재시작 후 데이터 손실 | Volume 연결 및 재시작 테스트 |
| 보고서 내용과 실제 환경 불일치 | 최종 실행 결과를 기준으로 보고서 작성 |
| 시연 영상 시간 초과 | 필수 시연 절차 사전 리허설 |
| 기능 추가에 따른 개발 지연 | 현재 기능 범위 이후 추가 개발 중단 |

# 15. 프로젝트 성공 기준

## 15.1 서비스 완성 기준

- 두 사용자 계정으로 로그인할 수 있다.
- 두 계정에서 동일한 장소 목록을 공유한다.
- 장소를 등록·조회·수정·삭제할 수 있다.
- 저장된 장소를 특정 날짜에 배정할 수 있다.
- 날짜별 방문 순서를 설정할 수 있다.
- 방문 상태를 변경할 수 있다.
- 두 사람이 각각 방문 전후 코멘트를 작성할 수 있다.
- 오래전에 저장한 미방문 장소를 확인할 수 있다.

## 15.2 클라우드네이티브 구현 기준

- 6개 컨테이너가 정상 실행된다.
- Nginx 역방향 프록시가 정상 작동한다.
- 두 백엔드가 기능별로 분리되어 있다.
- Redis를 통해 동일한 로그인 세션을 공유한다.
- MySQL에 영구 데이터를 저장한다.
- Volume Mount를 통해 DB 영속성이 유지된다.
- 직접 개발한 이미지가 Docker Hub에 업로드되어 있다.
- 설치 가이드에 따라 시스템을 재현할 수 있다.

## 15.3 제출 및 평가 대응 기준

- 프로그램의 핵심 기능을 모두 구현한다.
- 적절한 소스코드 네이밍과 상세한 주석을 작성한다.
- 시스템 구성도와 통신 절차도를 직접 작성한다.
- 모든 Docker 실행 명령어를 기록한다.
- 실행 화면과 검증 자료를 확보한다.
- 3분 이내 무편집 시연 영상을 제출한다.
- 편집 가능한 최종 보고서와 필요한 별첨자료를 제출한다.
- 보고서에 기재한 이름·포트·연결 관계가 실제 실행 환경과 일치한다.

# 16. 기대 효과 및 결론

OURSPOT은 연인과 가고 싶었던 장소를 저장하고, 이를 실제 데이트 일정으로 연결하며, 방문 전후의 생각을 함께 기록하는 소규모 웹 애플리케이션이다.

서비스 측면에서는 흩어진 장소 정보와 잊힌 데이트 계획을 체계적으로 관리할 수 있다.

기술적 측면에서는 여섯 개의 Docker 컨테이너를 기반으로 Reverse Proxy, 분리된 백엔드 서버, Redis 세션 공유, MySQL 데이터 저장 및 영속성을 구현한다.

특히 사용자가 한 서버에서 로그인하고 다른 서버에서 인증 상태를 유지하며 데이터에 접근하는 과정을 실제 서비스 기능과 연결함으로써, 마이크로서비스 아키텍처와 컨테이너 간 통신 구조를 구체적으로 검증할 수 있다.

본 프로젝트는 복잡한 부가기능보다 시스템의 정확한 동작과 재현 가능한 배포 환경을 중시한다.

**최종 목표는 실제로 사용할 수 있는 최소한의 커플 데이트 관리 서비스를 완성하는 동시에, 클라우드네이티브 과목의 필수 요구사항 및 평가 항목을 충족하는 것이다.**
